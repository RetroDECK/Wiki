## A Statement of Passion

When we the RetroDECK Team started this project many years ago, we had a bold vision: to create our dream retro gaming experience in an *all-in-one Retro Gaming Platform* called RetroDECK.

We wanted to build a platform that reflects our passion for the entire retro gaming space. Not just the most well-known games and consoles. But the countless communities projects and experiences that keep retro gaming alive.

Retro gaming is much bigger than emulation alone. 

**It includes:**

- Engine reimplementations such as **UZDoom** and other source ports.
- Complete game engines such as **Solarus** and **Open Surge** that keep the spirit of specific retro game genres alive.
- Emulators and multi-system emulation projects.
- Fantasy consoles such as **PICO-8**, alongside modern interpretations of retro hardware such as the **GameTank** and **Commander X16**.
- Dedicated pinball communities that keep their pinball halls lit.
- MUD communities that continue to keep decades-old servers alive.
- Retro computer enthusiasts who continue to create new software, games and hardware for the systems they love... year after year.
- Mods, standalone games, fan projects, romhacks and countless other creations.

Behind every one of these projects is a community with its own history, stories and memories.

There is an incredible amount of love for specific games, hardware, software and the shared experiences people grew up with. 

Many of these communities are small or easy to overlook, but they are an important part of what makes retro gaming so special.

## ⚠️ Important: Save and State Migration! ⚠️

**Important:** We strongly recommend backing up your important data before upgrading and **we will also prompt you to do so during the upgrade**. We are also taking secondary backups during the upgrade process.

**Why This Change Is Necessary?**

It's all about protecting your saves and save states.

RetroArch has introduced several new experimental cores for many systems, including higher-generation emulators that we tought was not possible before, such as Cemu, Vita3K, RPCS3, Xenia Edge and more. This expansion of new cores has been accelerated by rapid AI-assisted development.

As RetroArch expands its core support to include more emulators and maybe even game engines / other things, directory conflicts become more likely. The previous RetroDECK directory structure was based on the RetroArch structure as default, everything was jammed in there. This will cause issues with the new systems where RetroArch cores and standalone emulators could share save paths, potentially causing incompatible saves or overwriting existing data.  

To mitigate this we conducted a comprehensive audit of save files, save states and other directory structures across all components, including all RetroArch cores.

The conclusion of the audit was we needed to reduce potential compatibility conflicts between RetroArch cores and standalone emulators and make each component manage its own save and state structure independently under `saves/` and `states/`. We also identified areas where directory mappings became inconsistent over time (our fault) and we will remove all such discrepancies.

By isolating each component within its own directory structure: 

- We can protect user data and maintain long-term stability and better constitency. 
- Expand RetroDECK independently with new components and features and not be hindered by RetroArch's future development and design decisions. 

**Data Migration**

- Existing save files and states are **copied, backed up and relocated** to their new locations.
- Component settings and config files are updated to point to the new locations.
- No existing data is deleted.

### Save Pathing Changes

Each component manages its own dedicated directory under `saves/` and `states/`. We are adding a to `-SA` suffix (short for **Standalone**) to all standalone components that distinguishes them from RetroArch cores that use the same system name. For example, `saves/Cemu-SA/` is reserved for the standalone Cemu emulator, while `saves/RetroArch/wiiu/Cemu/` refers to the RetroArch Cemu core. 

RetroArch data and directory structure remains grouped under `saves/RetroArch/` and `states/RetroArch/`, keeping it separate from standalone component data.

The standalone components should also be aligned more closely to their real save structures. As they are today exposed into unknown RetroArch based save directories, with no way for users to know what the source directory is or how it reflects on each components standard documentation outside of the RetroDECK Wiki. 

### Example the new directory structure

```
saves/ or /states
├── RetroArch/
│   ├── gb/
│   ├── n64/
│   ├── psx/
│   ├── c64/
│   ├── snes/
│   └── ... <--- Ever Expanding RetroArch
├── Cemu-SA/
├── RPCS3-SA/
├── UZDoom-SA/
└── ... <--- Ever Expanding RetroDECK
```

## RetroDECK Framework

<img src="../../../wiki_icons/retrodeck/icon-framework.svg" width="75" alt="RetroDECK Framework Logo">


- **Removed the b suffix from versioning:** Following community feedback (very angry people on Lemmy that hates letters with a burning passion), we have dropped the `b` suffix from version numbers, so *let it `b` gone*.
- **Component Isolation:** Component-specific logic is now contained within its respective module and runs in a dedicated subsandbox on launch. Central functions that were specific to individual components have also been moved out of the main project and isolated within the component they belong to.
- **ES-DE JSON Translation:** Each component now defines its own ES-DE capabilities and configuration, replacing ES-DE's static XML lists: `es_find_rules.xml` and `es_systems.xml` and manual upkeep.
- **Startup / Shutdown Hooks:** Components can execute functions on `startup` and `shutdown` through `component_functions.sh`.
- **Unified Component Files:** Merged `component_update.sh` and `component_prepare.sh` into `component_functions.sh`.
- **Dynamic Component Loading:** Components are discovered and loaded dynamically at boot, automatically registering their tools, functions and ES-DE logic. This allows RetroDECK to detect available components, their capabilities and how they should run on each boot, while enabling support for components beyond the shipped internal components.
- **First Install:** Updated and changed first-install prompts to be more relevant and global, rather than component-specific.
- **Moved Global Functions to Framework:** Moved shared functions from the main application into the Framework component, including helper-file and folder-icon logic.
- **Updated Licences Files:** Condensed and updated the licences files to include all new components and features.

### ES-DE

<img src="../../../wiki_images/logos/es-de-logo.png" width="75" alt="ES-DE logo">

**Added:**

- **Our Own Naming Scheme:** As of 0.11.0 we have implemented our own naming scheme in ES-DE for all systems (we manually went over each one). All entries have been updated to clearly distinguish between **Libretro Cores** and **Standalone** versions using the new `(Libretro Core)` in addition to the old `(Standalone)` tag. We also introduced more metadata tags to convey more information to users, such as: `[Performance]`, `[Accuracy]`, `[Specialized]`, `[Legacy]` and `[Default]`.

**Changes:**

- **Hid Confusing Arcade Groupings:** ES-DE's catch-all ROM directories for arcade, which grouped multiple different emulators and systems into one (`pcarcade` and `consolearcade`). Were causing user confusion and issues, so they are now hidden and no longer used. We officially recommend using dedicated per-system Arcade directories instead such as `mame`, `fbneo`, `model2` and more. This to ensure the most accurate pre-configured setup for arcade games.
- **Easter Egg Splashes:** Moved Easter Egg splash logic from RetroDECK central functions to ES-DE's `component_manifest.json`. Moved Easter Egg artwork to ES-DE's assets instead of the main project.
- **ES-DE Configuration XMLs:** Removed the RetroDECK-specific `es_find_rules.xml` and `es_systems.xml` the dynamic loading now replaces them. ES-DE XML customization logic has been moved to the respective components.
